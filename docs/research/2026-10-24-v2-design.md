# V2 design research (2026-10-24)

Scope: quick pass, 4 searches. Items marked (unverified) come from general knowledge, not a fetched source. Gaps: Datadog, FireHydrant, PagerDuty, Foxglove, Formant, AutoStore and Ocado pages were not checked.

## 1. How incident tools present an incident
- Shared skeleton: summary, impact, timeline, contributing factors, action items, lessons ([incident.io](https://incident.io/blog/incident-post-mortem-template), [Rootly](https://rootly.com/blog/streamlined-incident-post-mortems-a-concise-template-ai-prompts-for-artefacts), [OneUptime](https://oneuptime.com/blog/post/2026-07-30-blameless-postmortem-template/markdown)).
- incident.io frames "contributors" (things that had to be true, or made it worse) instead of one root cause. Switchyard already does this by ranking causes by recovered parcel-minutes.
- Timelines are timestamped, with time since incident start, and each event links to its source ([incident.io](https://incident.io/blog/incident-post-mortem-template)).
- Impact is stated in business terms: users hit, revenue, SLO budget burned ([Augment guide](https://www.augmentcode.com/guides/incident-postmortem-template)). For Switchyard: parcels late, parcel-minutes, % below twin.
- Action items need owner, a verb, a measurable outcome and a deadline (practitioner standard, same source). Ours: "Best fix" with the recovered figure.
- 10-second read (inference): a title with severity and duration, then 3 headline numbers, then one sentence of cause and one of fix. Details sit below.
- Our current Post-mortem tab is a dense paragraph. The content is right; the layout is the gap.

## 2. Fleet and warehouse dashboards
- LocusHub shows live robot locations and states, units/picks per hour, a heat-map of busy zones, and a robot-density grid ([Locus](https://locusrobotics.com/locusone/ai-business-intelligence/locushub), [Locus monitoring](https://locusrobotics.com/locusone/ai-business-intelligence/warehouse-monitoring-dashboard-and-reporting)). Sources give no status colour scheme.
- Design write-ups on fleet dashboards stress one floor view plus a few KPI tiles ([Fuselab](https://fuselabcreative.com/warehouse-robotics-fleet-dashboard-design/)).
- Common conventions (unverified): dark control-room theme, green/amber/red for health only, one accent colour, monospace numbers, a status bar of counts.
- Takeaway: a heat-map (parcel-minutes lost per zone) is more persuasive than 200 coloured squares. Our floor has about 7 colours, with orange chutes competing with status colours.

## 3. Polished fast
- [Radix Colors](https://github.com/radix-ui/colors): MIT (per [bestofjs](https://bestofjs.org/projects/radix-colors)). 12-step scales with matching dark and light sets; steps are defined for backgrounds, borders and text, so contrast is largely handled. Check the repo LICENSE before shipping.
- [Open Props](https://github.com/argyleink/open-props): CSS custom properties for spacing, type, shadows, easing, with JSON exports. I believe it is MIT but the page fetch did not show it; verify the LICENSE file.
- Recipe: one sans (system-ui or Inter) plus one mono (JetBrains Mono, OFL) for numbers. A 4/8 px spacing scale, 3 type sizes, 1 accent, semantic tokens (`--bg`, `--surface`, `--text`, `--ok`, `--warn`, `--bad`) on `:root` and `[data-theme=light]`.
- Presentation stays in a tokens file; canvas colours read the same tokens, so the theme swaps without touching logic.

## 4. Onboarding a technical demo
- Dev tools that do this well (unverified, from general knowledge): Stripe docs (live example beside code), Linear and Vercel (empty states with one action), Observable and Grafana play (preloaded demo data).
- Pattern: land already loaded with the best incident, so nothing is empty. A 3-step strip: "1 Watch the dip, 2 Open the report, 3 Replay without the cause".
- Empty states say what is missing and give one button ("Analyse this run now").
- Tooltips on jargon only: "parcel-minutes", "noise band", "twin". Short, with a link to the docs.
- Deep links (`?preset=...&tab=postmortem`) so a LinkedIn post lands on the right screen.

## 5. Making an ops leader trust the numbers
- Show uncertainty beside every figure. Ours already has "± 3 %" and the noise band; surface it as a visual band on the chart.
- Provenance footer: version, seed, replay count, engine, "reproduce with this command". We have the text; make it a compact, copyable block.
- "How we know" in plain words: we rerun the same day 96 times with each cause removed. A one-line diagram beats a paragraph.
- Honest negative result: the "-6 parcel-min (-0 %)" line shows we report what does not explain the loss. Keep it, as a labelled "ruled out" row.
- Cite the twin's calibration limits (what it does not model) in a "Limits" disclosure.
- Determinism is a selling point: same seed, same result, anyone can verify.

## Recommendations for Switchyard V2 (ranked by impact per hour)
1. Post-mortem headline card: title, duration, 3 big numbers (loss, % below twin, parcels late), then cause and fix in one line each. About 2 h.
2. Tokens file plus Radix Colors dark/light, one accent, restrained status colours. About 3 h.
3. Chart: shade the dip, mark the fault ticks, show the noise band. About 2 h.
4. Load the best incident by default and add a 3-step guide strip. About 2 h.
5. Contributing-factors list as bars (parcel-minutes recovered, ± band) instead of prose; ruled-out causes greyed. About 2 h.
6. Provenance block with a copyable "reproduce" command. About 1 h.
7. Deep links per preset and tab, for posts and the README. About 1 h.
8. Floor: quieter palette, a loss heat-map toggle, a legend that doubles as a filter. About 3 h.
9. Tooltips for the 4 jargon terms plus a "Limits" disclosure. About 1 h.
10. Mono font for numbers, 8 px grid, and a README screenshot and GIF taken from the new layout. About 1 h.
